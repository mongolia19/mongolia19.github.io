>
> 近期，Anthropic 负责 Claude Code 工具链与 Agentic 开发者工作流的资深工程师（前 Google Chrome 工程总监）**Addy Osmani** 发表了一篇引发全球开发者热议的深度复盘：《*Your coding agents made you a manager*》（你的 Coding Agent 把你变成了工程经理）。
>
> 他犀利地指出：**如果你依然把 Coding Agent 当作高级自动补全或随叫随到的 Chatbot，你很快就会陷入 Prompt 疲劳、代码通胀与理解债务中；只有当你转换心态，把它当作一个全天候在岗的“初级/中级数字工程师”，并以 Engineering Manager (EM) 的组织管理思维来设立标准、卡点与闭环时，Agent 才能真正爆发 10 倍效能。**

> 本文深度拆解 Addy Osmani 总结的 10 条高杠杆管理法则，带你从“人肉打字机”平滑升级为高效驾驭 AI 团队的“超级工程经理”。

## 核心心智转变：为什么说 Coding Agent 把你变成了 EM？

在传统工作流中，程序员的主要时间花在：
1. 查文档、琢磨语法与 API；
2. 一行行在 IDE 里敲出实现细节；
3. 本地调试修复编译错误。

而在 Agentic 开发范式下，这些重体力活全被代理接管了。你面对的不再是一张空白的文件，而是一个不知疲倦、阅读速度惊人、但**缺乏全局业务语境、偶尔会产生幻觉、喜欢走阻力最小捷径**的“数字初级工程师”。

优秀的 Engineering Manager 是怎么带人的？
- 不替下属敲每一行代码，但会给出极其明确的 **Acceptance Criteria（验收标准）**；
- 绝不在下属没想清楚方案前就放任其大动干戈；
- 建立确定性的 CI/CD 和规范卡点，防止低级失误流入主干；
- 关注系统长期健康，警惕无意义的代码膨胀。

基于这套管理哲学，Addy Osmani 提炼出了以下 10 条黄金准则：

---

## 法则 1：给 Agent 一个可运行的判定条件（验证先行，拒绝口头承诺）

> **Rule 1: Give the agent a runnable check**

### ❌ 典型反模式（Anti-Pattern）
提完需求后，问 Agent：“改好了吗？”  
Agent 彬彬有礼地回答：“我已经为你优化了用户权限验证逻辑，并处理了边界异常，代码看起来非常完善！”  
结果你一把代码拉下来运行，服务直接 panic。

### ✅ EM 管理实践
**在软件工程中，“看起来对了”不叫完成；只有“跑通了测试”才叫完成。**

给 Agent 下发任务时，第一句话不要急着给实现细节，而是给它一个**客观、确定、可自动执行的 pass/fail 判定命令**：
- 一个具体的单元测试用例：`pnpm test tests/auth.spec.ts`
- 一个构建或类型检查脚本：`npm run build && npm run typecheck`
- 一个 CLI 或 API 的真实调用与期望输出：`curl -s http://localhost:3000/api/health | jq .status`
- 前端界面的视觉快照比对（Playwright/Puppeteer 截图）

**指令模板**：
> “请修复登录超时未刷新 token 的 bug。在声称任务完成之前，你**必须亲自执行** `pnpm test:auth` 并向我展示所有测试用例 PASS 的原始终端输出。不允许做出未经验证的推断。”

没有可运行验证的任务，是在给未来的自己埋雷。

---

## 法则 2：补充仓库所没有的“隐性上下文”（解释 Why，而非复述 How）

> **Rule 2: Supply context the repo cannot provide**

### ❌ 典型反模式
直接对 Agent 说：“把这个订单服务重构成支持多租户。”  
Agent 把全库代码扫了一遍，按照网上最通用的教科书方案大改一通，结果完全打破了你们团队针对特定支付渠道的历史妥协方案。

### ✅ EM 管理实践
现代 Coding Agent 拥有强大的 AST 分析和代码检索能力（grep, ripgrep, symbols）。它自己就能查出函数在哪里定义、类被谁继承——**你不需要当代码复述机**。

Agent 唯一看不见的是**代码库外部的隐性知识（Implicit Knowledge）**：
- **Why（业务动机）**：为什么当初要设计成两阶段提交？
- **Trade-offs（架构妥协）**：为什么我们宁愿牺牲轻微的一致性也要保高可用？
- **Edge cases（冷门边缘场景）**：某些下游渠道在每周日凌晨会返回特殊错误码；
- **Non-functional constraints（非功能约束）**：QPS 峰值是多少？内存上限只有 512MB。

**指令要点**：
向 Agent 交代背景时，假设它是今天刚入职的资深外援——它能秒读代码，但对你们业务部门的潜规则一无所知。把重点放在**限制边界、业务目的与不能破坏的历史原因**上。

---

## 法则 3：两次纠偏即沉淀为系统规则（CLAUDE.md / Skills 资产化）

> **Rule 3: Turn repeated corrections into system rules (The Two-Strike Rule for Rules)**

### ❌ 典型反模式
每次开启新会话，你都要疲惫地重复几句话：“不要用 lodash，用原生方法”、“组件必须加上 data-testid”、“提交前不要格式化未修改的文件”。

### ✅ EM 管理实践
在团队管理中，如果你需要对同一个问题纠偏两次，说明这不是人的问题，而是**SOP（标准作业程序）缺位**。

Addy 强调：“**如果你纠正了 Agent 同一个习惯两次，第三次绝不要用嘴说，立刻把它写进项目根目录的规则文件里。**”

- **项目级记忆（如 `CLAUDE.md` / `.cursorrules`）**：存放代码规范、常用验证命令、目录边界说明；
- **模块级指令 / 自定义 Skill**：把复杂的发布流程、环境检查、测试数据准备封装成 Agent 可调用的可执行脚本。

把纠错变成永久沉淀的组织资产，让后来的会话与 Agent 永远踩在过去的教训之上。

---

## 法则 4：先 Spec 后写代码（严禁裸写，对齐架构方案）

> **Rule 4: Agree on a plan/spec before code is written**

### ❌ 典型反模式
丢给 Agent 一句一句话需求，允许它“直接开干”。Agent 凭借强大的并行写代码能力，瞬间改动了 15 个文件。你 review 时发现基础设计思路全错了，只能全盘回滚。

### ✅ EM 管理实践
**Spec-Driven Development（规约驱动开发）** 是高阶使用 Agent 的分水岭：

```
           ┌───────────┐      ┌───────────┐      ┌───────────┐
           │   Spec    │ ───► │   Plan    │ ───► │   Build   │
           │ (做什么/边界)│      │ (分解原子任务)│      │  (分步落地) │
           └───────────┘      └───────────┘      └───────────┘
```

1. **Spec 阶段**：让 Agent 扮演架构师，先对你进行访谈提问，列出设计考量、影响范围与未明确的技术细节；
2. **Plan 阶段**：让 Agent 产出一份结构化的执行清单（Task Checklist），明确拆分为原子任务；
3. **人类审核（Sign-off）**：只有当你确认该计划无硬伤后，才输入 “Proceed” 允许它动第一行代码。

**一句话原则**：不要在代码里打草稿，要在 Spec 和 Plan 里打草稿。

## 法则 5：用硬规则代替软提示词（Prompt 只是建议，Hook 才是法律）

> **Rule 5: Enforce hard guardrails with Hooks and deterministic gates**

### ❌ 典型反模式
在 Prompt 里苦口婆心地加感叹号：“请务必不要执行 `git push --force`！千万不要修改 `config/production.json`！千万记得跑 linter！”

### ✅ EM 管理实践
LLM 本质上是概率模型。当上下文拉长、信息过载时，Prompt 里的禁令必然会出现**注意力衰减（Attention Drift）**。

一个成熟的工程团队绝不依赖“员工的自觉”来防范灾难，而是依靠**权限和网关**：
- **工具权限控制（Tool Permissions）**：限制只读/可写目录，阻断敏感系统调用；
- **Pre-tool / Post-tool Hooks**：在 Agent 执行写文件后，自动触发格式化检查；在 Agent 提出 commit 前，由 Hook 校验单测是否执行；
- **Git 分支保护与 CI 卡点**：无论 Agent 说了什么，CI 跑不过就不允许合入。

**记住**：提示词是给绅士的礼貌建议，自动化 Hook 才是约束数字员工的绝对法律。

---

## 法则 6：两次修不好果断重置上下文（两击出局法则）

> **Rule 6: Reset after two failed corrections: The 2-Strike Rule**

### ❌ 典型反模式
Agent 引入了一个奇怪的 bug。你让它修，它改了 A 处引发了 B 报错；你再让它修，它改了 B 引发了 C，并在上下文里疯狂堆叠数百行长调用栈。你在同一个聊天窗口里和它鏖战了 40 分钟，系统越来越烂。

### ✅ EM 管理实践
这在软件工程中叫做**沉没成本谬误（Sunk Cost Fallacy）**。

长上下文中塞满了失败的尝试、错误的假设和冲突的代码补丁，这些“上下文毒素”会严重误导模型的注意力分配。

**The 2-Strike Rule 操作规范**：
- 如果一个 Agent 连续**两次**自我修正都未能解决问题，**立刻停止在当前会话中打补丁**；
- 停下来，总结当前定位到的真正原因（甚至用简短笔记记录下坑点）；
- 执行 `/clear`、`/compact` 或开启一个全新的干净会话；
- 用提炼后的精确结论作为初始 Prompt，重新派发任务。

**90% 的顽固问题，在一个干净的上下文里都能在第一轮被秒级修复。**

## 法则 7：修剪陈旧规则，摒弃过时“咒语”

> **Rule 7: Prune rules and drop obsolete prompt habits**

### ❌ 典型反模式
项目里的 `CLAUDE.md` 或 `.cursorrules` 文件越写越长，堆砌了上千行，甚至还留着两年前的咒语：
- `Think step-by-step!`
- `Take a deep breath and work on this slowly.`
- 各种大写加粗的 `CRITICAL RULE: DO NOT EVER...`

### ✅ EM 管理实践
像 Claude 3.5 Sonnet、Claude 3.7 及更前沿的推理模型，内部早已内置了极其精密的多步推理（Extended Thinking）与工具编排机制。那些早期的“心理催眠法”在今天不仅毫无必要，反而会**抢占宝贵的上下文窗口，甚至让模型过度束手束脚、降低创造力**。

**定期规则审计清单**：
1. **删除冗余指导**：模型已经能默认做好的事情（如遵循语言标准语法），不要写进规则文件；
2. **遵守 200 行法则**：项目级规则文件尽量控制在 150~200 行以内，只保留**不可推断的专有约定**与**命令清单**；
3. **保持客观陈述**：把主观的情绪化词汇（“你必须”、“非常重要”）替换为客观的技术陈述（“提交前运行 `pnpm lint`”）。

## 法则 8：扩容的是“验证能力”，而非仅仅 Agent 数量（警惕协作税）

> **Rule 8: Scale verification, not just running agents (Beware the Orchestration Tax)**

### ❌ 典型反模式
听说了“多 Agent 并行”概念后，一口气开了 10 个 Agent 同时开发 10 个需求。结果半小时后，10 个分支同时发来合并请求，代码风格冲突、改动交织在一起，你一个人坐在屏幕前 Review 到深夜崩溃。

### ✅ EM 管理实践
软件工程经典名著《人月神话》揭示过一个真理：向延期的项目增加人手，只会让项目更加延期。

**对于 AI Agent 也是如此。并发运行 10 个 Agent，吞吐量绝不会线性提升 10 倍，因为你个人的 Review 带宽成为了整个系统的最大瓶颈——这就是所谓的“编排协作税”（Orchestration Tax）。**

要想真正规模化释放并发 Agent 的威力，**前提是你的自动化验证体系能够等比例扩容**：
- **独立的 Worktree 隔离**：每个 Agent 只能在独立的 git worktree 中作业，互不干扰；
- **子代理辅助评审（Sub-agent Review）**：引入专门的 Security Agent、Linter Agent 先过滤一遍初级问题；
- **全自动化的回归测试套件**：无需人工干预，合并前自动化测试全部通过才推到你的桌面。

没有自动化测试网的“多 Agent 并行”，只是一场制造技术债的高速灾难。

---

## 法则 9：下放执行权，绝不下放裁决权（警惕“认知投降”）

> **Rule 9: Delegate the implementation, never the judgment (Avoid Cognitive Surrender)**

### ❌ 典型反模式
看到 Agent 贴出的 PR 全绿，单测都通过了，瞄都不瞄一眼直接点“Merge”。至于代码底层引入了什么架构耦合、有没有潜在的内存泄漏、逻辑符不符合长远规划，完全不管不问。

### ✅ EM 管理实践
Addy Osmani 提出了一个极具警示意义的词汇：**Cognitive Surrender（认知投降）**。

当工具过于强大时，人类最容易犯的错误就是“思维偷懒”——把思考的主权彻底拱手相让。然而，**AI 没有皮肤受试（Skin in the game），它不用在凌晨三点被线上报警电话叫醒，但你必须**。

| 事项 | 下放给 Agent（Delegation） | 人类工程师保留（Ownership） |
| :--- | :--- | :--- |
| **执行层面** | 编写样板代码、转换数据结构、单测用例编写、排查编译报错 | **品味（Taste）、美感、极简主义** |
| **架构层面** | 根据既定模块接口编写胶水层代码 | **系统边界划分、数据模型设计、外部依赖引入决断** |
| **安全与业务** | 扫描语法错误、生成 mock 数据 | **合规性、资损防范、核心商业逻辑取舍** |

**请牢记**：你可以把打字的劳力 100% 外包给 Agent，但你必须保留 100% 的架构品味与技术裁决权。

## 法则 10：衡量系统健康，而非产出规模（警惕“理解债务”）

> **Rule 10: Measure systems, not output volume (Know what NOT to build)**

### ❌ 典型反模式
公司和团队开始比拼 KPI：“我们团队这个月借助 AI 生成了 50 万行代码，生产力提升了 300%！”  
半年后，代码库膨胀成无法维护的迷宫，团队里没有一个人能讲清楚整个系统的调用链。

### ✅ EM 管理实践
当生成代码的边际成本趋向于零时，**代码的阅读成本、维护成本和认知开销却在呈指数级上升**。Addy 称之为 **“Comprehension Debt”（理解债务）**。

代码是负债，功能才是资产。真正优秀的工程管理者，在 AI 时代更看重的是**克制与减法**：
- **优秀的衡量指标**：
  - PR 交付前置时间（Cycle Time）；
  - 线上变更失败率与回滚频率（Revert Rate）；
  - 系统架构的自解释性与简单度（Simplicity）。
- **优秀的工程素养**：
  - 知道什么时候**不该写代码**，直接复用既有模块；
  - 鼓励 Agent 在完成任务的同时**删除多余的代码和废弃依赖**。

**少即是多**：在 AI 时代，判断一个工程师水平的高低，不再看他能写多少代码，而是看他能用多么克制清晰的架构解决问题。

## 总结：从 Coder 到 Director 的三大支柱

回顾 Addy Osmani 的 10 条建议，我们可以将它们归纳为驱动现代 Coding Agent 的三大支柱：

```
       ┌────────────────────────────────────────────────────────┐
       │                现代 Coding Agent 三大支柱                │
       └───────────────────────────┬────────────────────────────┘
                                   │
         ┌─────────────────────────┼─────────────────────────┐
         ▼                         ▼                         ▼
 1. Spec-Driven            2. Evidence-Based         3. Loop-Engineered
   (规约先行)                 (证据主义)                 (闭环工程化)
 • 先 Plan 后编码           • 绝不轻信口头承诺          • 用 Hook 代替口头提醒
 • 明确边界与 Why           • 依靠可执行命令验证        • 沉淀项目 rules 与 skills
 • 人类掌舵架构裁决         • 保持干净的上下文窗口      • 以自动化测试护航多 Agent
```

1. **Spec-Driven（规约驱动）**：不打无准备之仗。让 Agent 先梳理需求和原子计划，把不确定性消灭在编码之前。
2. **Evidence-Based（证据主义）**：拒绝幻觉。让代码和测试输出说话，没有可执行验证的任务绝不视为完工。
3. **Loop-Engineered（闭环工程化）**：用系统对抗遗忘。把散乱的人工提示词，沉淀为自动化的 Hooks、规则文件与隔离工作流。

**AI 时代并没有降低对软件工程能力的要求，反而将其拔高到了一个新的维度。**  
那些只会熟练背诵语法、机械翻译需求的程序员会被浪潮吞没；而那些懂得系统设计、善于定义规则、具备严密架构裁决力的“AI 工程经理”，正在迎来属于他们的黄金时代。
