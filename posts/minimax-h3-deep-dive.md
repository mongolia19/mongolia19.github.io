# 开源打平 Seedance 2.3，MiniMax H3 到底做对了什么？

> **作者**：卡兹克  
> **标签**：`MiniMax H3` | `视频生成` | `多模态` | `开源模型` | `AIGC`

---

这几天，我把 MiniMax H3 的官方文章、开源仓库、模型配置和 API 文档顺着翻了一遍。

一开始我也以为，重点无非是 2K、15 秒、原生双声道，再加一个开源。

这几个词很适合做发布会大字报。放在一起，热闹是够热闹了。但真正让我停下来看的，是官方演示里那句有点离谱的指令。

参考视频 1 的希区柯克镜头运动，让图片 2 里的人唱歌，歌声参考音频 3。

你仔细想想，这已经不是普通的视频提示词了。

里面有镜头运动，有人物身份，有动作，有音色，还规定了每份素材各自扮演什么角色。过去要做这件事，创作者得在动作迁移、人物参考、口型驱动、音色克隆和视频生成之间来回倒腾。每个环节一个入口，每个入口一套参数，最后再交给剪辑软件擦屁股。

H3 想干的事更狠一点。它想让你用一句自然语言，把这些关系全说清楚，然后由同一个系统接住。

这才是 H3 最值得聊的地方。

先把边界交代清楚。MiniMax 在 7 月 31 日发布 H3，随后开放了模型权重和推理代码。到我写这篇文章时，GitHub 仓库已经有 5000 多颗 Star。官方把它叫作通用全模态生成系统，支持文字、图片、视频和音频输入，输出最长 15 秒、24 FPS、最高 2K，并带 32 kHz 原生立体声。

但「完整系统」和「已经开放的模型」不是一回事。

H3 的完整流水线其实分成三段。前面是 H3-Context-IR，负责看懂你给的各种素材，以及素材之间那一团乱麻似的关系。中间是 H3-Base，负责生成 768P 的画面和声音。后面是 H3-Regenerate-2K，把低分辨率结果和原始上下文重新喂回系统，再生成 2K 成片。

目前真正开放权重的是中间的 H3-Base。Context-IR 依赖多个托管模型和多阶段工作流，只提供 API。2K Regeneration 也还没有开放，只能走官方 API 验证。

所以，网上那些「H3 完整开源，拉下来就能本地跑 2K」的说法，多少有点着急了。

更准确的讲法是，MiniMax 开放了 H3 最重、也最核心的生成基模，同时把最影响官方成片质量的前处理和 2K 重生成留在云端。开发者可以本地跑 768P，也可以把本地 H3-Base 接进官方的 Context-IR 和 Regeneration API，拼出完整工作流。

这个区别挺重要。开源社区拿到了发动机，但官方赛车上那套导航和精调系统，还没有全拆下来。

回到 H3 的技术选择。它做的第一件事，不是把 Transformer 堆得更深，而是重新定义「提示词」到底是什么。

以前的视频 caption，大多是在描述目标画面。一个女人站在雨里，镜头缓慢推进，远处有霓虹灯。模型学的是文字和目标视频之间的对应关系。

H3 面对的输入复杂多了。它不光要描述目标，还要说清上下文和目标的关系。哪张图负责人物身份，哪段视频只参考运镜，哪段音频提供音色，原视频里的背景音乐要保留多少，人物在第几秒开始说话，又在第几秒闭嘴。

MiniMax 把这套东西叫 Contextual Omni Representation。

名字有点大，翻成大白话，就是先把一次创作任务写成一份足够完整的「导演执行单」。

为了做这份执行单，官方说大部分素材要消耗大约 10 万 token 的推理，再压缩成平均 4000 token 左右的上下文表示。开源仓库里的样例很能说明问题。一句普通的人物说话指令，经过 Context-IR 后，会被展开成人物定义、素材保留关系、分镜时间线、口型停止时刻、环境音和非叙事音乐等一整套结构化描述。

我看到这段的时候，第一反应不是「提示词变长了」。

而是视频模型开始拥有自己的中间语言了。

编译器不会把人写的高级代码直接扔给机器执行。它会先转成中间表示，再做优化和调度。H3-Context-IR 干的事很像这一层。用户继续讲人话，系统则把人话翻译成生成模型更容易执行的任务描述。

这里也藏着 H3 的第一个判断，语言不是众多输入里的一个普通模态，而是组织其他模态的胶水。

这话听着有点哲学，但落到训练上很具体。以前的文生视频、首尾帧、人物参考、动作参考、音色参考和视频编辑，往往各有各的任务头，甚至各练各的专家模型。H3 尽量早地混合这些数据和任务，用自然语言表达参考与编辑关系，不再给模型画死十几个功能抽屉。

抽屉少了，组合空间反而大了。

接住这套中间语言的，是 H3-Base。它的核心是一个 330 亿参数的稠密单流 Transformer，共 50 层，隐藏维度 5376，56 个注意力头。大约 130 亿参数位于 AdaLN 相关分支，纯推理时可以预计算并缓存调制结果，因此部署时不必把这部分参数全部加载进来。

这里的「单流」很关键。

文字由 H3-Encoder 编码。视觉素材同时经过 H3-Encoder 和 VisualVAE。音频走独立的 AudioVAE。进入主干之前，系统把这些表示打包成一条统一的多模态序列，再交给同一个 H3-Omni Transformer。

注意力层和 FFN 层里没有专门为视频或音频单独搭一套结构。模态差异主要留在输入输出层和 AdaLN 分支。主干负责在同一个空间里预测视频 latent 和音频 latent，最后再各自解码成画面与左右声道。

这跟「先生成无声视频，再让另一个模型配音」差别很大。

后者像拍完默片再找音效师补素材。H3 更接近拍摄现场，动作、口型、对白、环境声和音乐从生成阶段就互相看得见。它不保证每次都配得完美，但技术路线已经从后期拼接转向联合建模。

为了让一条序列同时装下这么多东西，H3 在压缩上花了不少力气。

它的 VisualVAE 是时间因果视频自编码器，空间先压缩 16 倍，时间压缩 4 倍，latent 通道数是 24。进 Transformer 前，视觉 latent 又按 1 乘 2 乘 2 做 patchify。合起来看，一个视觉 token 对应原画面上约 32 乘 32 的空间区域，时间维保持 4 倍下采样。

这个设计看着像一串枯燥参数，背后其实是视频生成最现实的账本。

分辨率翻倍，帧数增加，token 数量都会往上窜。注意力面对的不是多几行文字，而是一整段时空网格。压缩做得差，细节先糊。压缩做得保守，序列又长到算不动。MiniMax 称新 VAE 带来了 4 倍有效序列长度收益，原生 2K 的成本空间，很大一部分就从这里抠出来的。

声音也被压成 token。H3-AudioVAE 把 32 kHz 音频压成每秒 40 个 latent token，左右声道共用同一套编码器和解码器，但分别处理，最后再合成立体声。

你想想看，24 FPS 的视频和 40 Hz 的音频 latent 要在同一条生成过程中保持时间关系，模型还得知道画面里那扇门什么时候关上，撞击声该落在哪一帧。H3 用三维多模态 RoPE 表达时间、高度和宽度位置，至少给这种对齐搭起了坐标系。

当然，序列统一之后，计算量也跟着上来了。官方披露，多模态上下文让序列长度方差扩大了 3 倍，理解和生成的 workload 差异也更明显。训练侧因此把理解与生成的计算调度分开优化，再处理样本内部异构计算和样本之间的负载均衡，端到端训练吞吐提升接近 30%。

模型本身也训练了原生稀疏注意力，用来降低长序列成本。不过这块需要泼一点冷水，初始开放版本只提供全注意力推理，稀疏注意力实现还要等后续更新。

也就是说，论文里的效率优势和你今天拉代码跑出来的效率，不能直接画等号。

官方给的 SGLang 示例用 4 张 GPU 做张量并行。至于普通创作者手里那张消费级显卡，先别急着幻想本地 2K 全模态自由。330 亿稠密主干、Qwen3-VL-32B 编码器、视觉 VAE 和音频 VAE 一起上，门槛还在机房那边。

说到 2K，H3 最有意思的反而不是分辨率数字，而是它没有走常见的专用超分路线。

传统超分拿到低清视频后，主要根据像素邻域和学到的视觉先验补细节。脸上的纹理可以补，小字和品牌标识就容易开始瞎猜。因为超分模型看不到最初那堆参考图、人物关系和创作指令，它只知道眼前这段低清片子。

H3-Regenerate-2K 把 768P 结果和原始多模态上下文一起送回 H3 基模，让它重新生成高分辨率版本。低清视频提供运动和构图，原始上下文负责提醒模型，那块招牌写的是什么，那个人应该长什么样，产品包装有哪些细节。

这不是把旧片放大，而是拿着原始剧本和样片重拍一遍。

我觉得这条路线很漂亮。它把超分也变成了「参考和编辑」的一种，继续复用基模已经学会的能力，不再为 2K 单独养一个只会补像素的专家。

但漂亮归漂亮，问题也很现实。重生成会不会改掉 768P 版本里已经正确的动作和构图，跨镜头一致性能保持到什么程度，小字恢复到底有多稳定，这些都需要系统性评测。官方目前没有发布完整 Tech Report，也没有给出足够细的第三方基准。

所以我不想跟着样片喊「视频生成被终结了」。

样片只能证明上限，工作流要看失败率。

H3 真正值钱的商业点，倒是已经很清楚了。API 目前 768P 每秒 0.5 元，2K 每秒 0.8 元，单独从 768P 重生成 2K 每秒 0.3 元。做一条 10 秒 2K 视频，输出成本是 8 元。Context-IR 按 token 另计，输入每百万 token 5.8 元，输出每百万 token 23 元。

价格不是唯一门槛。广告、电商和品牌内容更在意文字别写错、Logo 别变形、人物跨镜头别换脸，以及导演修改一句话后，系统只改该改的部分。H3 把多模态参考、原生音画和重生成放进一条流水线，瞄准的就是这些生产问题。

过去大家比的是谁能生成一段更炸的 Demo。下一阶段比的，可能是谁更像一个听得懂修改意见的制作团队。

这里还有个挺有意思的细节。H3 开放了两个任务 checkpoint。FL2VA 负责文生视频、首帧、尾帧和首尾帧。Ref2VA 负责图片、视频、音频的全参考生成。它们都经过 CFG 蒸馏，推理框架已经接到 SGLang、vLLM、Diffusers 和 ComfyUI。

这说明 MiniMax 并没有只扔一坨权重出来刷开源声量。它明显希望 H3 进入开发者的真实工具链。

但它用的是 MiniMax H3 Community License，不是常见的 Apache 2.0 或 MIT。再加上 Context-IR、稀疏注意力和 2K Regeneration 尚未全部开放，我更愿意称它为「开放权重的完整生成基座」，而不是一句带过的「完全开源」。

把话说准，反而更尊重这次开放本身。

写到这里，我又回头看了一眼最开始那句指令。参考视频的运镜，让图片里的人唱歌，声音参考另一段音频。

过去我们会把它拆成五六个任务，分别交给五六个模型。H3 试着把它重新写成一句话，再让一条统一的生成链路去执行。

从技术史上看，很多通用系统的出现，都伴随着中间语言的成熟。操作系统把硬件差异藏在系统调用后面，浏览器把不同机器藏在 Web 标准后面，编译器把底层指令藏在高级语言后面。

视频生成现在也走到了类似的路口。

创作者不该记住十几个模型分别吃什么参数。他只需要讲清楚自己要什么，哪些素材该保留，哪些关系该变化。至于任务怎么拆、模态怎么对齐、算力怎么调度，应该由系统处理。

H3 还远没把这件事做完。官方自己也承认，多模态理解、模型规模和画面精细度都还有提升空间。完整技术报告没出，几个关键模块没开，真实生产的稳定性也要等更多人下场撞墙。

但方向已经很清楚了。

它不是又造了一台更清晰的短视频老虎机。

它在试着造一套视频创作的语言。

而语言一旦长出来，接下来变化的就不只是画质，而是谁可以成为导演，以及一个人能调动多大的制作能力。

想想还是挺兴奋的。
