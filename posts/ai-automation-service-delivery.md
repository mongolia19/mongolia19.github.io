# 别把 AI 自动化卖成聊天机器人：一个能交付的 n8n 项目，应该长什么样

很多人把 AI 自动化服务讲成“给企业装一个 Agent”。这句话太大，也太虚。客户真正会付钱的，是某个反复发生的动作终于不用靠人盯着：线索不再漏、工单不再堆、内容初稿不再从空白开始。

但只要把模型输出直接接到发邮件、改报价、写数据库，项目就很容易从“提高效率”变成“制造事故”。真正值得卖的，不是一段提示词，而是一条能解释、能接手、能出错后回退的业务流程。

## 先找一件小而痛的事

第一个项目不要做“全公司 AI 化”。找一件每周重复、责任人明确、做完能核对的事情。

拿线索分流举例。一家小型服务公司把咨询收在官网表单、邮箱和私信里。一个靠谱的流程可以这样跑：

1. 新线索进来，先校验字段、去重。
2. 模型把文本抽成结构化字段：行业、预算、紧急程度、需求类型。
3. 规则层把结果分成 `hot`、`warm`、`cold`、`review`。
4. 高意向线索写入 CRM 并提醒销售；缺字段、低置信度或敏感内容进入人工复核。
5. 每一步留日志，失败时通知负责人。

这就够了。它并不神秘，但它能被验收。

## 模型只能负责它擅长的那一段

大模型很适合三件事：分类、抽取、起草。

它不适合替客户做最终承诺。价格、退款、合同、对外回复、涉及个人信息的判断，都应该留一层规则或人工审批。把这个边界画清楚，反而更容易签单，因为客户知道你不是来兜售不可控的“自动驾驶”。

一个最小的技术链路通常就是：

```text
Webhook / 邮箱 / 表单
  -> 字段校验和去重
  -> LLM 输出 JSON
  -> Schema 与业务规则校验
  -> CRM / 表格 / 工单系统
  -> 人工审批或异常告警
```

`n8n` 这类编排工具很适合把这条链路搭出来。它有大量集成和模板，但工具并不是交付物。交付物是流程的控制权：谁能改凭据、失败后谁收到提醒、人工怎么重跑、客户怎么查一条记录为什么被分到这个队列。

## 报价时，卖三件东西

比起一口价承诺“帮你节省多少人力”，把服务拆成三段更稳。

| 阶段 | 客户拿到什么 |
| --- | --- |
| 流程诊断 | 现状图、字段清单、风险点、验收口径 |
| MVP 搭建 | 一条主流程、测试样本、操作手册、交接演示 |
| 运行维护 | 告警、月度复盘、提示词和连接器更新 |

第三方成本单列。模型 API、自动化平台、数据库、短信和邮件都不要藏在固定报价里。用量一变，谁承担成本必须在项目开始时说清楚。

## 什么叫“能交付”

交付当天，别只发一张工作流截图。至少留下：

- 节点说明和凭据归属；
- 正常、缺字段、重复、超时、人工驳回的测试清单；
- 告警接收人和升级规则；
- 模型、提示词、连接器的版本记录；
- 数据保留、删除和权限变更方式。

这些东西看上去不性感，却决定客户三个月后还能不能继续用，也决定你会不会被叫回去救火。

## 一个朴素的冷启动法

先找三家熟人企业，不推销工具，只问三件事：每天最耗时间的重复动作是什么？漏掉一次会有什么损失？最后谁来确认结果？

用脱敏数据做一个三分钟演示。演示里必须有输入、自动处理、人工复核、最终记录和失败提醒。第一单的目标不是制造收入神话，而是拿到一组前后对比：处理时间、漏单数、人工修订率、异常恢复时间。

把这些留下来，第二单才不是从零开始。
